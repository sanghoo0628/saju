> **복사 전 최신 변경사항(2026-11-16):** 사용자는 **A(공통·인증·사주)만** 진행한다. 현재 흐름은 **추천 프로필 3명 무료 확인 → 선택 상대당 500원 → 대화 요청 → 상대 수락 → 채팅**이다. 기존 대화 재결제 없음, 수신자 수락·답장 무료. 아래 보존 프롬프트의 ‘결제 후 3명 공개’ 규칙은 적용하지 않는다. [DECISIONS.md](DECISIONS.md), [TEAM_CONTRACT.md](TEAM_CONTRACT.md)를 함께 전달하고 기존 C 모듈을 중복 구현하지 않는다. 공통 Node 버전은 24 계열이다.

아래 내용을 새 Codex 작업에 붙여 넣으세요. 함께 제공된 문서 폴더를 작업공간에 놓거나 첨부하면 됩니다. 이 문서의 목표는 기획 재논의가 아니라, 실제 코드 확인 후 단계별 구현을 시작하는 것입니다.

대학생 대상 사주 기반 소개팅·활동 추천 서비스를 개발해줘.

첨부한 문서를 먼저 읽어:
1. CODEX_HANDOFF.md — 통합 제품·기술 명세, 현재 상품, 역할, API, 데이터, 결제·채팅 계약
2. TASKS_AND_ACCEPTANCE.md — 개발 순서와 완료 기준
3. ACTIVITY_BOOKING_PLAN.md — 활동 추천·예약 중개 확장
4. references/MATCHING_ALGORITHM_ORIGINAL.md — 기존 알고리즘 원문
5. references/PDF_PLAN_EXTRACT.md — 팀 공유 PDF 텍스트
6. .env.example — 실제 키가 없는 환경 변수 템플릿

현재 구현 상태나 저장소가 이미 존재한다고 가정하지 말고 먼저 작업공간, AGENTS.md, package.json, git 상태와 remote를 확인해. 기존 코드와 팀원 변경을 보존하고 문서와 차이가 있으면 기록해. 다른 프로젝트 저장소를 재사용하지 마.

프로젝트 목표:
- 외부 사주 API의 상세 결과를 정규화하고 자체 규칙으로 상대를 추천한다.
- 현재 MVP는 사주 결과 → 프로필 등록 → 500원 결제 → 추천 3명 → 대화 요청 → 상대 수락 → 채팅이다.
- 다음 단계는 둘 다 가능한 시간·예산·이동 범위 안의 활동 추천과 예약 중개다.
- 지금은 P0를 먼저 완성하고 P1/P2는 확장 경계를 마련해.

문서 안의 '확정 사실', '개발 기본안', '운영 전 미정'을 구분해. 특히 다음을 지켜:
- PDF의 HMAC 문이과 점수와 사주60/선호25/만남15 모델은 별도 전략이다.
- legacy_demo_v1은 오락용 데모이며 실제 사주 궁합으로 표현하지 않는다.
- 사주 조합별 승인 규칙은 아직 완성되지 않았다. 임의 점수·LLM 점수로 실제 모델을 완성했다고 보고하지 않는다.
- hybrid를 계산할 수 없으면 not_ready로 처리한다. 알고리즘이 미완이어도 공통 흐름과 나머지 P0 기능은 구현한다.
- 현재 상품의 공개 인원은 주문당 3명이다. 원문 초안의 '하루 5명'을 동시에 적용하지 않는다.
- 실제 API·상품·키·예약 파트너가 없으면 adapter와 표시된 개발용 mock을 사용한다. mock 성공을 실제 결제·예약 성공으로 표시하지 않는다.

새 프로젝트라면 Next.js App Router + TypeScript + pnpm + Supabase로 시작해. 기존 합리적인 프로젝트 설정이 있으면 유지해. 버전은 현재 공식 문서를 확인하고 lockfile로 고정해.

첫 구현 순서:
1. 공통 화면/폴더, 패키지·스크립트, README, .env.example을 준비.
2. Supabase browser/server/admin 클라이언트 경계와 getCurrentUserId() 공통 함수를 준비.
3. DB 마이그레이션, RLS, 공개 프로필 DTO, 테스트 계정·데이터 생성 절차를 준비.
4. 사주 adapter/mock과 프로필, MatchingStrategy 인터페이스, legacy 데모를 연결.
5. 서버 주문과 Groble ref·웹훅 검증·중복 방지·제공 트랜잭션을 구현.
6. 주문별 저장된 3명 공개, 대화 요청/수락/거절, 1:1 채팅과 차단·신고를 연결.
7. 권한·동시 요청·환불 역순·재접속 테스트, 타입 검사와 빌드를 수행하고 실패를 수정.

팀 역할은 A=공통/인증/사주, B=DB/프로필/매칭/RLS, C=결제/채팅이다. 팀원 코드가 있으면 역할 경계에 맞춰 협업하고 중복 구현하지 마. 공통 계약을 코드 타입과 문서로 공유해.

핵심 기술 계약:
- 사용자 식별자는 Supabase auth.users.id(UUID), TS에서는 string.
- buyer_id/sender_id는 검증된 로그인 컨텍스트에서 결정.
- Groble 웹훅은 사용자 로그인을 요구하지 않고 서명으로 인증.
- sellerReference와 merchantUid로 주문을 연결. 원문 body 검증과 이벤트 멱등 처리.
- payment_status와 fulfillment_status를 분리.
- 결제 완료와 결과 제공을 DB 트랜잭션/복구 가능한 상태로 처리.
- paid+fulfilled인 본인 주문만 프로필 공개. 후보 부족 시 부분 제공 금지.
- 수신자가 수락해야 채팅 가능. 수신자는 별도 결제 불필요.
- 정렬된 참여자 쌍에 고유 제약을 둬 중복 방 생성 방지.
- 메시지와 사진까지 RLS/접근권한 검증. 관리자 키 브라우저 노출 금지.
- 활동 추천에는 제휴 수수료율을 반영하지 않음.
- 외부 링크 클릭은 예약 확정·수익 확정이 아님.

검토나 계획만 작성하고 멈추지 말고, 가능한 구현과 검증을 계속해. 외부 계정·비밀키가 없으면 필요한 변수와 연결 절차를 문서화하고 그와 독립적인 작업을 끝내. 비밀키는 채팅이나 git에 출력하지 마.

원격 저장소와 main 반영 지시가 확인된 경우 해당 지시대로 진행해. 대상이나 지시가 없으면 로컬 결과를 완성하고 원격 반영에 필요한 정보만 알려줘. 실서비스 배포·운영 DB 변경·실결제 실행은 해당 작업의 사용자 지시와 환경 범위를 확인해.

개발 결과로 다음을 남겨:
- 실행 가능한 코드와 실제 변경 파일
- .env.example, 설치·실행 README
- 마이그레이션/RLS와 재현 가능한 테스트 절차
- 구현 완료/목업/외부 설정 대기/미구현 상태표
- 실행한 검사와 결과, 남은 차단 요인
- C 담당자가 바로 사용할 서버 사용자 ID 함수·주문 API·채팅 계약

사용자에게 진척은 간단히 공유하고, 중요한 외부 정보가 꼭 필요한 경우에만 질문을 모아줘.
