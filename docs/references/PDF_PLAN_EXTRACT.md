무료로 사주 풀이와 본인 점수를 제공하고, 500원 결제 후 점수 합이 0에 가까운 상대 3명의 프로필을
공개한다. 상대가 대화 요청을 수락하면 웹에서 일대일 채팅을 진행한다. 이 문서는 서비스 흐름부터 구
현 구조, 권한, 결제, 채팅, 역할 분담과 검증 기준까지 정리한다.

서비스 이용 흐름




기획 요구와 첫 버전 권장안
• 기획 요구: 문과는 양수, 이과는 음수이며 기본 숫자는 1~10,000이다. 사주 풀이와 점수는 무료, 프
로필 3명 공개는 500원이다.

• 권장안: 500원 상품에 공개된 3명에게 대화 요청하는 기능을 포함한다. 상대의 수락과 답장은 무료
이며 대화 성사를 보장하지 않는다.

• 점수는 실제 사주 계산과 별개인 오락용 매칭 규칙이다. 같은 입력의 점수는 유지한다.

• 사주 프로그램의 실행 방식과 Groble의 500원 결제 및 협찬 조건은 개발 전에 확인한다.

1 시스템 구성과 사주 프로그램 연결
권장 구성은 Next.js 웹과 서버 API, Supabase 인증과 DB 및 Realtime, 기존 사주 프로그램, Groble이다.
별도의 채팅 서버를 처음부터 만들지 않고 기존 기능을 조합한다.




구조도는 서비스 간 연결을 나타낸다. 사주 호출·점수 계산·매칭·주문 검증은 서버에서 수행한다. 브라우
저의 Supabase 접근은 RLS가 허용한 본인 정보와 채팅 데이터로 제한한다.

기존 사주 프로그램 상태별 연결 방법

 현재 상태                 연결 방법

 HTTP API 제공           Next.js 서버가 API를 호출한다.

 Python 함수 또는 라이브러리    함수를 실행하는 얇은 HTTP API 서버로 감싼다.

 화면으로만 실행              API나 라이브러리 제공 여부를 먼저 확인한다. 연동 가능하다고 가정하지 않는다.




배포와 개발 중 처리
• 배포한 웹 서버는 개발자 노트북의 localhost에 바로 접근할 수 없다. 사주 프로그램도 접근 가능한 서
버 환경에 배포해야 한다.

• 생년월일 외에 출생 시간·양음력 등 필요한 입력, 응답 형식, 이용 조건을 확인한다.

• 프론트는 가짜 사주 응답으로 먼저 개발하고 실제 API를 나중에 교체한다. 동일한 전체 입력과 프로
그램 버전의 결과는 캐시한다.

• API 실패 시 재시도 화면을 제공하고, 실패한 결과를 정상 사주 풀이로 저장하지 않는다.

2 고정 점수 생성과 매칭 규칙
점수 생성
매번 난수를 새로 뽑지 않고, 서버의 비밀 키를 이용한 해시로 생년월일을 1~10,000의 정수에 대응시킨
다. 같은 생년월일에는 같은 기본 숫자가 나오며, 서로 다른 생년월일의 숫자가 겹치는 것은 허용한다.

 항목              계산 규칙

 기본 숫자           1 + (HMAC 결과를 정수로 변환한 값 mod 10,000)

 문과 점수           +기본 숫자

 이과 점수           −기본 숫자

 두 사람의 거리        abs(내 점수 + 상대 점수)

 추천 순위           거리 오름차순 후 고정된 동점 기준을 적용하여 상위 3명 선택


생년월일 형식은 YYYY-MM-DD 등 하나로 통일한다. 비밀 키는 브라우저에 전달하지 않고, 점수와 계산
버전을 저장한다. 비밀 키 변경 시 기존 점수가 바뀌지 않도록 저장된 점수를 우선 사용한다.

내 점수가 양수 3500일 때

 상대         점수                       거리                     순위

 A          −3,490                   10                     1

 B          −3,530                   30                     2

 C          −3,600                   100                    3

 D          −2,900                   600                    4




후보 필터와 결과 유지
• 본인, 탈퇴·비활성 계정, 공개 미동의 계정, 서로 차단한 계정은 제외한다.

• 연애 매칭을 원한다면 성별과 매칭 희망 조건을 별도로 입력받고 조건에 맞는 후보 안에서 계산한다.
현재 점수식 자체는 성별을 판단하지 않는다.

• 반대 계열이 주로 추천되지만 반드시 반대 계열만 선택하는 규칙은 아니다. 문이과 간 매칭으로 제한
하려면 별도 필터를 합의한다.

• 주문마다 공개한 3명을 저장하여 새로고침해도 같은 결과를 반환한다. 재구매를 도입하면 이전 공개
상대를 제외하는 정책을 적용한다.

• 생년월일·계열 수정 및 점수 재생성 정책은 출시 전에 합의한다. 서버는 클라이언트가 보낸 점수나 순
위를 신뢰하지 않는다.

3 데이터 저장과 접근 권한
Supabase는 회원 인증, 데이터베이스, 사진 저장, 실시간 전달을 담당한다. 프로필 저장과 프로필 공개
권한은 별개의 문제이므로 모든 회원에게 전체 프로필 조회를 허용하지 않는다.

 테이블                  주요 저장 내용

 profiles             user_id, 닉네임, 소개, 사진 경로, 계열, 공개 동의·활성 상태

 private_birth_data   user_id, 생년월일과 사주에 필요한 비공개 입력

 fortune_results      user_id, 본인 점수, 사주 풀이, 계산 및 프로그램 버전

 orders               주문 ID, 구매자, 금액, 상태, 참조값, Groble 거래 식별자

 match_results        주문 ID, 공개 상대 ID, 순위, 계산 당시 거리

 chat_requests        요청자, 수신자, 대상 구매 결과, 대기·수락·거절 상태

 conversations        채팅방 ID, 두 참여자 ID, 생성 시각

 messages             메시지 ID, 채팅방 ID, 작성자 ID, 본문, 작성 시각

 blocks / reports     차단 관계, 신고 대상과 사유, 처리 상태




권한 설계
• 본인 사주·생년월일·학교 이메일은 본인과 허용된 서버 작업만 접근한다. 상대에게는 필요한 프로필
카드 정보만 전달한다.

• 유료 프로필은 서버가 결제 완료와 match_results를 확인한 뒤 제공한다. 화면에서만 숨기고 전체 정
보를 미리 내려보내지 않는다.

• messages는 채팅방 참여자만 조회·전송한다. sender_id는 로그인 사용자와 같아야 하며 차단 상태도
검사한다.

• 사진도 공개 범위에 맞춰 Storage 정책을 적용한다. 제한 공개가 필요하면 비공개 버킷과 만료되는
서명 URL을 사용한다.

• RLS는 행 단위 접근을 제한한다. service_role 같은 관리자 비밀 키는 서버에만 두고 브라우저 번들에
포함하지 않는다.

학교 인증
허용 학교 이메일 도메인 검사와 실제 메일 인증을 함께 사용한다. 학교 이메일 인증이 현재 재학생 신분
을 완전히 보증하는 것은 아니므로 화면 표현을 구분한다. 허용 도메인 목록은 팀이 확인한다.

4 Groble 결제와 프로필 공개
권장 상품은 500원으로 프로필 3명 열람과 해당 상대에게 대화 요청을 제공하는 형태다. 상대 수락이나
답장은 보장하지 않으며 구매 전에 이를 표시한다.

결제 처리 순서
1. 로그인과 매칭 후보 수를 확인한다. 후보가 3명 미만이면 결제를 막는다.

2. 서버가 500원 주문과 추측하기 어려운 참조값을 만들고 구매자와 연결한다.

3. Groble 결제 링크에 ?ref=참조값을 붙여 사용자를 이동시킨다.

4. Groble이 서버의 웹훅 주소로 결제 완료 이벤트를 전송한다.

5. 서버가 서명, 결제 상태, 금액, 상품, 주문 참조값을 검증한다.

6. 하나의 DB 트랜잭션에서 결제 상태를 갱신하고 추천 3명을 match_results에 저장한다.

7. 결과 화면이 주문 상태를 조회한다. 권한이 생성되었으면 해당 3명만 공개한다.

상태와 예외 처리

 상황                   처리 기준

 결제 후 복귀가 웹훅보다 빠름     결제 확인 중 화면을 보여주고 서버 주문 상태를 재조회한다.

 같은 웹훅 여러 번 도착        거래 ID 고유 제약과 주문 잠금 등으로 한 번만 처리한다.

 결제 완료 화면 URL 직접 방문   서버 확인 전에는 프로필을 공개하지 않는다.

 결과 화면 새로고침           저장된 동일한 3명을 반환하며 새 주문을 만들지 않는다.

 결제 중 후보 탈퇴 또는 비공개    재선정하거나 환불 절차로 넘긴다. 결과가 3명 미만인 상태로 완료하지 않는다.

                      주문 상태와 열람 권한을 정책에 따라 갱신한다. 이미 열린 채팅의 처리도 합의한
 취소 또는 환불
                      다.




Groble 담당자에게 확인할 내용
• 500원 결제 지원 여부, 협찬에 포함된 수수료 범위, 결제 테스트 방법.

• 웹훅 서명 검증 방식, 재전송 정책, 취소·환불 이벤트와 상품 설정.

1건의 수익 = 500원 − 결제 비용 − 사주 호출 비용 − 운영 비용. 수수료가 전액 면제된다고 가정하지 않
는다. 사주 결과 캐시로 동일 입력의 불필요한 호출을 줄인다.

5 대화 요청과 실시간 채팅
프로필 공개에서 채팅까지
구매자는 공개된 3명에게 대화를 요청한다. 상대는 무료로 수락하거나 거절하고, 수락할 때 서버가 두 사
람의 채팅방을 만든다. 상대방에게도 대화에 필요한 요청자 프로필을 확인할 수 있는 권한을 부여한다.

• 서버가 요청자에게 해당 프로필 열람 권한이 있는지 확인한다. 반복 요청과 중복 요청을 제한한다.

• 수락은 요청 수신자만 할 수 있다. 동일한 두 사람의 기존 채팅방이 있으면 재사용하여 중복 생성을
방지한다.

• 거절되면 자동으로 다른 사람을 추가 공개하지 않는 것을 기본안으로 두되, 최종 구매 정책은 팀이 합
의한다.

메시지 전달 구조




메시지를 DB에 먼저 저장하고 Supabase Realtime으로 전달한다. 첫 버전은 설정이 간단한 Postgres
Changes로 시작할 수 있다. 규모가 커지면 비공개 채널 권한을 갖춘 Broadcast 전환을 검토한다.

권한과 재접속 처리
• 메시지 조회·전송은 참여자만 허용한다. Realtime 구독에도 접근 권한이 적용되도록 구성한다.

• 차단 시 새 메시지 전송을 막는다. 차단 이후 기록 조회·구독 처리 정책도 일관되게 적용한다.

• 재접속 시 마지막 수신 메시지 이후의 기록을 DB에서 가져온다. 메시지 ID로 중복 표시를 제거하고
시각과 ID 기준으로 순서를 맞춘다.

• 첫 버전에는 웹 대화 목록, 텍스트 채팅, 차단·신고를 포함한다. 사진 전송, 읽음 표시, 입력 중 표시,
푸시 알림은 후순위로 둔다.

대화 요청이나 새 메시지는 사용자가 웹을 다시 열었을 때도 확인할 수 있어야 한다. 푸시 알림을 만들지
않아도 대화 목록과 대기 요청 목록은 제공한다.

6 팀원 세 명의 역할 분담
전체 개발을 3명이 맡는 기준이다. 각 담당자가 화면과 서버 기능을 함께 소유하고, 초기에는 가짜 데이
터와 합의된 API 형식으로 병렬 개발한다. 역할은 담당 범위를 기준으로 나눴으며 실제 일정에 따라 조정
한다.

팀원 A 가입과 사주 결과
• 공통 화면 구조와 UI 컴포넌트, 로그인 및 학교 이메일 인증, 입력 폼을 구현한다.

• 사주 프로그램 실행 방식을 확인하고 API 어댑터, 가짜 응답, 오류·재시도 처리, 결과 캐시와 무료 결
과 화면을 담당한다.

• 공통 배포 설정과 환경 변수 목록을 정리한다. 점수 계산은 B의 공통 함수를 호출한다.

완료 기준: 학교 이메일 인증 후 입력을 제출하면 실제 사주 풀이와 고정 점수가 표시되고, API 실패도 처
리된다.

팀원 B 프로필과 매칭
• 공통 DB 구조 초안과 마이그레이션 충돌 정리, 프로필 등록·수정·공개 동의 및 사진 접근 정책을 담당
한다.

• 고정 점수 계산, 후보 필터, 거리순 추천, 주문별 추천 저장과 결과 조회, 프로필 카드를 구현한다.

• 주문별 열람 권한과 채팅 참여자 RLS를 담당하여 C의 결제·채팅 작업을 지원한다.

완료 기준: 유효 후보 3명을 규칙대로 선정하고, 결제한 본인만 구매 결과를 조회한다. 제3자는 프로필과
채팅 기록에 접근하지 못한다.

팀원 C 결제와 채팅
• Groble 상품·주문 연결, 웹훅 검증·중복 처리, 결제 확인 화면과 취소·환불 상태 처리를 담당한다.

• 대화 요청·수락·거절, 중복 없는 채팅방 생성, 메시지 저장과 Realtime 연결, 대화 UI와 차단·신고를 구
현한다.

• B와 결제 완료 트랜잭션을 함께 연결한다. 주문·채팅 기능의 DB 마이그레이션은 C가 작성하고 B가
통합한다.

완료 기준: 결제 한 번으로 동일한 3명이 열리고, 수락한 두 사람만 실시간 메시지를 주고받는다.

작업량 균형과 공동 책임
C는 외부 결제와 실시간 기능을 함께 맡으므로 B가 권한 정책과 DB 트랜잭션 통합을 지원하고 A가 공통
UI와 배포를 맡는다. 세 명이 함께 API 계약, 구매 정책, 매칭 공개 조건을 먼저 확정하고 통합 검증은 공
동 수행한다.

7 API 계약과 개발 순서

8 출시 전 검증과 확인 사항
필수 검증
 • 같은 생년월일·계열로 다시 접속해도 점수가 같고, 순위 계산과 동점 처리가 일정하다.

 • 본인·비공개·탈퇴·차단 계정이 후보에서 제외되고, 후보 3명 미만이면 결제가 시작되지 않는다.

 • 실제 테스트 결제 한 건이 주문과 연결되고, 서명·금액·상품 불일치 이벤트는 거부된다.

 • 웹훅 재전송과 동시 요청에도 결제가 한 번만 처리되고 결과 3명이 중복 생성되지 않는다.

 • 결제 복귀가 웹훅보다 빨라도 정상 처리되고, 새로고침은 같은 결과를 보여준다.

 • 미결제 계정과 다른 주문 소유자는 프로필을 조회하지 못한다. 사진 URL로도 권한이 우회되지 않는
 다.

 • 두 계정이 요청·수락 후 채팅할 수 있고, 제3자는 기록 조회·구독·전송을 할 수 없다.

 • 연결을 끊었다 다시 접속해도 메시지 누락·중복이 없고, 차단 후 새 메시지가 거부된다.

 • 사주 API 실패, 결제 중 탈퇴, 취소·환불, 공개 동의 철회 시 화면과 권한 상태가 일치한다.

착수 시 합의하거나 확인할 사항
외부 확인: 사주 프로그램 API·배포 가능 여부·입력과 이용 조건, Groble 500원 결제·수수료·웹훅·환불 조
건. 팀 합의: 허용 학교 이메일, 이용 대상과 희망 조건, 생년월일·계열 수정, 재구매·중복 추천, 공개 철회
및 환불 이후 채팅 정책.
