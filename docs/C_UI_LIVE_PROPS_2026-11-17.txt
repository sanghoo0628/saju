C 결제·채팅 UI의 실제 데이터 연결 준비
2026-11-17 / codex/c-payment-chat

현재 상태
GitHub를 fetch해 확인했으며 이번 작업 시작 시 A/B의 추가 커밋은 없었다.
A 공통 앱이나 실제 로그인·결제를 연결한 것은 아니다.
재사용 컴포넌트가 실제 인증 사용자와 B 공개 프로필을 받을 수 있게 준비했다.
이 문서가 이전 C_UI_RECOVERY 문서의 컴포넌트 props 설명보다 최신이다.

바뀐 파일/계약
- src/types.ts: ChatProfile { userId, nickname, major: string | null, tone? }
  여기서 src/는 packages/payment-chat-ui/src/를 뜻한다.
- B의 ProfileCard는 위 세 필드를 포함하므로 그대로 전달할 수 있다.
  score, 학번/year, 생년월일, 이메일, 사주 원문은 요구하지 않는다.
- PaymentDialog와 ChatPanel은 catalog.ts, MY_ID, demo-client.ts를 import하지 않는다.
- 가상 인물 변환은 App.tsx에만 두었다. App.tsx 자체는 여전히 로컬 데모다.

ChatPanel 추가/변경 props
  currentUserId: string              // A가 확인한 Supabase user.id
  profiles: readonly ChatProfile[]   // B가 공개를 허용한 추천/대화 상대 정보
  demo?: {
    onAcceptRequest?: (id: string) => Promise<void>;
    onReply?: (id: string) => Promise<ChatMessage>;
  }

- 기존 onDemoAccept/onReply 최상위 props는 위 demo 객체로 옮겼다.
- demo를 생략하면 상대 수락/답장 체험 버튼과 데모 안내가 나타나지 않는다.
- rooms/requests는 해당 currentUserId의 데이터만 화면에 남긴다.
  프론트 필터는 방어적 처리이며 서버/RLS 권한 검사를 대체하지 않는다.
- 대화 내부 key는 currentUserId + room.id다. 계정이 바뀌면 기록·초안 상태를 새로 만든다.
- 이전 계정의 선택 ID가 남아도 모바일 목록이 숨겨져 갇히지 않는다.
- 상대 프로필을 아직 읽지 못했어도 '상대방'과 뒤로 버튼을 표시한다.
- currentUserId가 없으면 A 쪽에서 로그인 화면을 표시하고 ChatPanel을 마운트하지 않는다.
- 추천 3명 외의 기존 대화/받은 요청 상대도 B의 권한이 허용하는 공개 프로필을 읽어 전달한다.
  공개 프로필이 없다고 가상 인물을 대신 넣지 않는다.

호출 예시 (변수와 콜백은 A/C 연결 코드에서 제공)

  <ChatPanel
    key={currentUserId}
    currentUserId={currentUserId}
    profiles={publicProfiles}
    rooms={rooms}
    requests={requests}
    selection={selection}
    onSelect={setSelection}
    listLoading={listLoading}
    listError={listError}
    onReload={reloadLists}
    onAccept={acceptRequest}
    onReject={rejectRequest}
    api={api}
    busy={busy}
  />

A는 로그인 변경 시 목록/선택/결제 상태도 초기화하고 이전 요청을 중단한다.
서버는 항상 실제 로그인 세션으로 구매자/작성자를 결정한다.
브라우저 props의 currentUserId를 서버 인증 수단으로 사용하면 안 된다.

PaymentDialog 추가/변경 props
  profile: ChatProfile
  paymentAction:
    | { kind: 'checkout', onCheckout: () => void }
    | { kind: 'demo', onConfirm: (mode: DemoPaymentMode) => void,
        onFinishDelayedPayment: () => void }

- 기존 onConfirm/onFinishDelayedDemo는 paymentAction의 demo 분기로 옮겼다.
- 실제 앱에서는 kind: 'checkout'을 명시한다. 이때 버튼은 '500원 결제하기'다.
- 실제 앱 분기에는 데모 시나리오·가상 결제 완료·데모 안내가 나타나지 않는다.
- onCheckout에는 주문 ID 보존 및 검증된 HTTPS 결제 주소로 이동하는 A/C 연결 함수를 넣는다.
  결제 복귀 라우트와 주문 ID 보존 방식은 실제 공통 앱 통합 시 구현해야 한다.
- onRecheck는 기존 주문의 상태 조회만 한다. 결제 완료는 서버 웹훅으로 확인한다.
- 기존 대화방을 받은 chat_available 상태는 '대화 이어가기'로 안내한다.
- 환불 대기/환불 완료/취소 상태에서 새 결제나 대화 요청 버튼을 만들지 않는다.

호출 예시

  <PaymentDialog
    key={`${currentUserId}:${selectedProfile.userId}`}
    profile={selectedProfile}
    state={checkout}
    busy={busy}
    actionError={actionError}
    paymentAction={{ kind: 'checkout', onCheckout: openVerifiedCheckout }}
    onClose={closePayment}
    onRequest={requestChat}
    onRecheck={recheckSameOrder}
    onRetry={retryCurrentCheckout}
  />

검증
- npm run test:all: 기존 165개 통과 (Vitest 104 + C Node 61).
- npm run test:ui: 새 컴포넌트 렌더링 검사 13개 통과. 위 명령과 별도다.
- 합계 178개 통과.
- npm run typecheck: 공통 엄격 타입 검사 통과.
- npm run demo:build: UI 타입 검사(새 테스트 포함)와 Vite 빌드 통과.
- 추가 런타임/테스트 패키지 설치나 잠금 파일 변경은 없다.
- UI 검사는 B 공개 프로필 호환, 기본 실제 결제/데모 분리, 상대방 표시,
  다른 로그인 사용자의 요청 방향, 무관한 계정 데이터 숨김, 누락 프로필,
  기존 대화 재사용과 취소/환불 상태의 액션을 검증한다.
- UI 검사는 React 서버 렌더링으로 수행하므로 클릭 이벤트/effect/실제 인증을 검증한 것은 아니다.
  이전 작업의 브라우저 오류 복구 검증과 구분한다.

실행 전 준비
루트 npm ci 및 packages/payment-chat-ui의 pnpm install이 필요하다.
루트 test:all은 기존 B/C 검사이고, UI 의존성이 필요한 test:ui는 별도 명령으로 유지했다.
A가 pnpm으로 통일할 때 test:ui와 새 UI 테스트/타입 검사를 함께 유지한다.
새 npm 스크립트 외 의존성/잠금 파일에는 변화가 없다.
