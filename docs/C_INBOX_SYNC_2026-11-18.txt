C 대화 요청·수락 결과 자동 반영
2026-11-18 / codex/c-payment-chat

문제와 구현
기존 화면은 본인의 버튼 동작 뒤에만 목록을 새로 읽었다.
다른 사용자가 요청을 보내거나 수락하면 현재 화면이 계속 대기 상태로 남을 수 있었다.
이번 변경은 기존 인증된 GET API로 요청/방 목록을 주기적으로 확인하고 화면을 갱신한다.

새 모듈
packages/payment-chat/src/inbox-session.ts
- createInboxSession({ userId, client }): 요청 목록·방 목록 갱신 컨트롤러.
- reconcileInboxSelection(selection, userId, snapshot): 선택한 요청과 실제 방의 연결 확인.
- InboxSelection: 기존 ChatPanel의 ChatSelection과 동일한 타입. UI 쪽 export도 유지했다.

동작
- 생성만으로 요청하지 않는다. start() 때 최초 조회와 기본 5초 주기 조회를 시작한다.
- 요청/대화방을 병렬로 조회하고 두 목록이 성공한 뒤 함께 반영한다.
  이는 프론트 표시의 일괄 갱신이며 두 HTTP 요청의 DB 스냅샷을 한 트랜잭션으로 만든다는 뜻은 아니다.
- 100개씩 페이지를 읽고 ID로 중복을 합친다. 매번 첫 페이지부터 읽어 새 요청/상태 변경을 확인한다.
- 기본 최대 10페이지(종류별 최대 1,000개)이며 한도 도달 시 Complete 플래그가 false다.
- 잘린 목록은 UI에 최근 내역부터 표시한다는 안내를 추가했다.
  추가 페이지 UI와 대량 사용자의 조회 최적화는 공통 앱 운영 범위에 맞춰 보완할 수 있다.
- 선택한 요청이 accepted이고 그 두 사람의 방이 서버 목록에 있으면 해당 방으로 전환한다.
- 수락 상태만 먼저 보이고 방이 아직 조회되지 않았다면 준비 중 안내와 조회 버튼을 표시한다.
  브라우저가 방이나 결제 권한을 만들어 내지 않는다.
- 선택하지 않은 새 요청은 배지/목록에만 반영한다. 다른 대화를 보고 있는 사용자를 강제로 이동시키지 않는다.
- 거절 결과는 대기 중과 구분한다. 보낸 요청 결과를 프로필에서 다시 볼 때 새 결제창을 열지 않는다.
- 취소/환불/거절 이후 재요청 정책을 추가한 것은 아니다.

오류와 수명
- 일시적 실패 시 마지막 성공 목록을 유지하고 오류 안내를 표시한다. 다음 주기/수동 조회로 복구한다.
- 기본 15초 시간 제한이 지나면 대기를 끝내고 재시도할 수 있다.
- 401/403은 요청·방 목록을 지우고 자동 조회를 중단한다.
  실제 인증이 확인된 새 사용자 컨텍스트에서 세션을 다시 생성해야 한다.
- refresh() 중복 호출은 진행 중 작업을 공유한다.
- 요청 전송/수락/거절 뒤 refresh(true)는 이전 읽기를 중단하고 최신 결과를 다시 읽는다.
- 화면/계정 해제 후 응답은 반영하지 않으며 이전 사용자 정보를 내부에서도 지운다.
- 외부에서 스냅샷을 수정해도 내부 요청·참여자 목록에 영향을 주지 않는다.
- accessDenied 플래그로 권한 오류를 구분해 선택을 즉시 해제한다.
- 진행 중이거나 일시적 오류인 스냅샷은 새로 선택한 방을 삭제한 것으로 판단하지 않는다.
- 성공한 완전한 목록에서 사라진 현재 요청/방은 선택을 해제한다.
  페이지가 잘린 경우에는 보이지 않는다는 이유만으로 제거됐다고 판단하지 않는다.

화면 연결
- App.tsx가 inbox-session을 실제 사용하도록 바꿨다. App 자체는 여전히 가상 사용자 데모다.
- ChatPanel의 기존 필수 props는 유지했다.
- 선택적 listHasMore prop만 추가했다. 생략하면 이전과 같은 표시다.
- 데모의 환불 대기용 프로필 상태 변경도 읽기/쓰기 트랜잭션과 같은 큐에서 처리한다.
  동시 목록 조회가 이 상태 변경을 덮어쓰지 않는지 별도 검사했다. 실제 DB 정책 변경은 아니다.
- 메시지 수신용 messageSource/MessageSession과 목록 갱신은 별개다.
  이번 요청/수락 반영은 WebSocket이 아닌 인증 HTTP 주기 조회다.
- messages RLS/Realtime publication, 과금/환불 규칙과 B 마이그레이션은 변경하지 않았다.

A 연결 순서 예시 (인증 사용자마다 새로 생성)

  const inbox = createInboxSession({ userId: verifiedUserId, client: paymentChatApi });
  const unsubscribe = inbox.subscribe(state => {
    setRequests(state.requests);
    setRooms(state.rooms);
    setListLoading(state.loading);
    setListError(state.error);
    setSelection(current => reconcileInboxSelection(current, verifiedUserId, state));
  });
  inbox.start();

  // 요청 보내기/수락/거절이 서버에서 성공한 뒤
  await inbox.refresh(true);

  // 탭으로 돌아올 때도 inbox.refresh(true)로 최신 목록을 확인할 수 있다.
  // 실제 로그아웃/사용자 변경/화면 해제 시
  unsubscribe();
  inbox.dispose();

- snapshots의 userId는 표시 범위를 구분하기 위한 값이다. 서버 인증으로 신뢰하면 안 된다.
- 부모의 선택 변경에는 함수형 setState를 사용해, 갱신 도중 사용자가 고른 다른 대화를 덮어쓰지 않는다.
- listHasMore는 데이터가 있고 !requestsComplete 또는 !roomsComplete일 때 전달할 수 있다.
- 브라우저 로그인과 서버 인증 user.id, 공통 Supabase 프로젝트를 맞추는 A/B 작업은 여전히 필요하다.

검증
- 신규 inbox-session/데모 동시 실행 Node 검사 20개 통과.
- 신규 UI 렌더링 검사 4개 통과.
- npm run test:all: 기존 Vitest 104 + C Node 129 = 233개 통과.
- npm run test:ui: 18개 통과. 합계 251개.
- npm run typecheck / npm run demo:build / git diff --check 통과.
- HTTP 통합: 두 개의 로그인 세션을 흉내 내 한쪽의 요청을 다른 쪽에서 읽고,
  상대 수락 후 원래 요청자가 같은 방으로 연결되는지 확인했다.
- 브라우저: 별도 로컬 서버에서 모의 결제 후 대기 화면을 열어 두고,
  화면의 수락 체험 버튼을 누르지 않은 채 다른 동작으로 상대를 수락시켰다.
  이후 자동 목록 조회로 방 전환 및 메시지 전송을 확인했다. 브라우저 오류 로그 없음.
- 검증에서 사용자가 체험 중인 4174/4175 서버에 초기화 API를 호출하지 않았다.
  검증은 별도 4176/4177 서버의 가상 데이터로 진행했다.

범위와 남은 검증
실제 A 로그인/Next.js 앱, B Supabase 설정, 실제 두 사용자 간 통신은 미연결이다.
실제 Supabase Realtime 및 Groble 결제/복귀/환불 검증과 네이티브 PostgreSQL 동시성 10개도 남아 있다.
main/B 브랜치와 실제 외부 DB를 수정하지 않는다.
A/B에게는 기존 답변을 받으면 이번 변경과 최신 커밋을 함께 공유한다.
