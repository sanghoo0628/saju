# 활동 추천·예약 중개 개발 계획

> 최신 상품 변경: 추천 프로필 3명 무료 열람 → 선택 상대당 500원 대화 권한. 아래 이전 과금 설명은 배경 자료이며 [최신 결정](DECISIONS.md)이 우선합니다. 이번 구현은 A 범위입니다.

작성일: 2026-11-16. 이 문서는 최신 PDF의 결제·채팅 MVP 이후 확장 범위를 정의한다. 제휴처, 예약 API, 수수료율이 확보되었다는 뜻은 아니다.

## 1. 현재 결정과 확장 가설

| 구분 | 내용 |
|---|---|
| MVP 기준 | 500원으로 추천 프로필 3명 열람과 해당 상대에게 대화 요청. 상대 수락·답장은 무료이며 대화 성사를 보장하지 않는다. |
| 확장 아이디어 | 수락한 두 사람에게 시간·이동·예산에 맞는 활동을 제안하고 예약을 연결한다. |
| 초기 검증 제안 | 대학가 공방·보드게임 카페 등 3~5곳과 직접 제휴를 검토한다. 확정 파트너는 없다. |
| 미정 | 실제 예약 공급자, API 접근 권한, 판매 주체, 정산 기준, 취소·환불·노쇼 규정, 중개 수수료율. |

초기 논의의 ‘매칭 확정비’는 수익화 아이디어였다. 현재 구현 기준은 PDF의 500원 상품이다. 서로 다른 과금 정책을 합쳐 추가 결제를 만들지 않는다. 사주·소개·예약을 결합했다는 이유만으로 시장 차별성이나 수익성이 입증되었다고 표현하지 않는다. 검증할 가치는 대학생의 생활권·시간표·예산에 맞춰 실제 약속을 쉽게 정하는 경험이다.

## 2. 단계별 구현

### P1: 활동 추천과 예약 연결

수락된 채팅방에서 활동 카드를 함께 보고 계획을 제안한다. 상대가 같은 계획 버전을 확인한 뒤 외부 예약 페이지로 이동하거나 예약 요청을 제출한다. 외부 링크 방식과 직접 제휴 방식은 공급자별로 구분한다.

- 외부 링크만 제공하면 ‘예약 페이지 열기’로 표시한다. 클릭·복귀만으로 예약 완료를 기록하지 않는다.
- 수동 제휴는 ‘예약 요청 접수 → 업체 확인 중 → 예약 확정/불가’로 처리한다. 운영자가 업체 확인 근거와 시각을 기록해야 확정된다.
- 가격·재고를 확인하지 못한 카드는 ‘예약 가능 미확인’으로 표시한다. 가짜 잔여석이나 확정 문구를 만들지 않는다.
- P1은 활동 카탈로그·요청·확인 기록만으로 검증할 수 있다. 외부 API가 없다고 예약 API를 임의로 만들어 실제 연결된 것처럼 표시하지 않는다.

### P2: 계약된 예약 API

실제 계약과 명세를 확보한 공급자에 한해 조회·예약·취소를 구현한다. 가격·재고 재조회, 예약 중복 방지, 웹훅 검증, 실패 복구와 정산 대사를 추가한다. 외부 요청이 시간 초과되면 즉시 재예약하지 말고 공급자 예약 상태부터 조회한다.

공통 `BookingProvider`는 `capabilities`와 함께 `searchActivities`, `getQuote`, `checkAvailability`, `createBooking`, `getBooking`, `cancelBooking`을 정의한다. 지원하지 않는 기능은 `unsupported`로 반환하고 UI에서 숨기거나 수동 절차로 전환한다. 공급자별 금액 단위·시간대·식별자를 어댑터에서 정규화한다.

## 3. 두 사람에게 맞는 활동 계산

점수 계산 전에 두 사람 모두 가능한 시간, 각자의 허용 이동시간·개인별 총예산, 피하고 싶은 활동, 영업시간·소요시간·인원 조건을 동시에 만족하는 계획을 만든다. 총예산에는 각자가 실제 부담하는 매칭비·활동비·필수 예약비를 포함한다. 수신자가 내지 않은 500원을 수신자 비용에 더하지 않는다.

계획은 `starts_at`, `timezone`, `duration_minutes`, `venue_id`, `activity_id`, `cost_per_user`, `travel_minutes_per_user`, `availability_status`, `quote_expires_at`을 가진다. 시간은 UTC로 저장하고 표시 시간대를 별도로 관리한다. 이동시간이 추정이면 출처와 확인 시각을 보존한다.

초기 활동 정렬식은 다음과 같다. 모든 하위 값은 0~100이며 검증 전 제품 정책이다.

`ActivityScore = 0.45 × 양방향 활동선호 + 0.30 × 이동·예산 적합도 + 0.15 × 시간 적합도 + 0.10 × 양쪽이 확인한 사주 테마 선호`

사주 해석으로 제안한 ‘차분한 대화’, ‘새로운 경험’은 사용자가 직접 공감 여부를 확인한 뒤 선호에 반영한다. 두 사람 중 한 명이라도 테마를 확인하지 않았다면 동일 비교 목록 전체에 `(45×선호 + 30×이동예산 + 15×시간) / 90`을 적용한다. 후보별로 다른 점수 척도를 섞지 않는다.

태그 출처는 `saju_interpretation`, `user_confirmed`, `observed_behavior`로 구분한다. 하위 점수 산식·가중치 버전과 계산 근거를 저장한다. 사주로 실제 성격·안전성·연애 성공률을 단정하지 않는다. 제휴 수수료율은 추천 점수에 넣지 않으며 협찬 노출은 별도로 표시한다.

## 4. 데이터·권한·상태 계약

| 데이터 | 최소 내용 |
|---|---|
| `activity_partners` | 업체, 담당 운영자, 공급 방식, 계약·정산 조건 버전 |
| `activities` | 장소, 태그, 소요시간, 인원, 가격 출처·확인 시각, 예약 링크 |
| `date_plans` | 채팅방, 계획 버전, 양쪽 비용·이동시간, 각자 동의 시각 |
| `booking_requests` | 계획 버전, 요청자, 내부 참조값, 공급자 예약 ID, 상태·사유 |
| `booking_events` | 이벤트 ID, 출처, 발생·수신 시각, 검증·처리 결과 |
| `commission_ledger` | 예약, 계약 버전, 정산 기준액, 수수료, 취소 조정, 정산 상태 |

계획·예약 요청은 해당 채팅방 참여자만 조회·제출한다. 업체에는 이행에 필요한 최소 정보만 전달하고 생년월일시·사주 원문은 전달하지 않는다. 예약 확정·취소·정산 상태는 검증된 서버 작업이나 권한 있는 운영자만 변경한다.

예약 상태는 `requested → pending_confirmation → confirmed / unavailable / cancelled`를 기본으로 한다. 확정 후 취소 요청은 `cancellation_requested → cancelled / cancellation_rejected`로 별도 추적한다. 결제 상태·방문 완료 상태는 예약 상태와 분리한다. ‘취소 요청’은 환불 완료가 아니다.

가격·시간·활동·부담액이 바뀌면 계획 버전을 올리고 양쪽 동의를 다시 받는다. 확정 직전 최신 가격·재고를 확인한다. 변경을 알리지 않고 대체 상품이나 추가 금액을 결제하지 않는다. 같은 예약 요청의 재시도는 같은 멱등 키를 사용하며 공급자 예약 ID에는 고유 제약을 둔다.

## 5. 수익과 정산

매칭 결제 주문과 활동 예약·결제는 별도 식별자와 상태로 관리한다. Groble 매칭 결제가 활동 상품 결제까지 지원한다고 가정하지 않는다. 활동비를 직접 받으려면 판매 주체·상품 제공·환불·정산 구조부터 확인한다.

- 예약 성사 수수료는 실제 제휴 계약이 있고 계약상 조건이 충족된 건에만 기록한다. 외부 링크 클릭 자체에는 매출을 붙이지 않는다.
- ‘활동 추천 중개 수수료’와 ‘예약 수수료’가 같은 거래의 같은 대가이면 한 번만 계산한다. 별도 요금은 제공 가치·부담 주체·계약과 사전 표시가 있을 때만 검토한다.
- 예시 `2인 활동비 40,000원 × 수수료 15% = 6,000원`은 가상 계산이다. 실제 견적·순이익·확정 수수료가 아니다.
- 활동 거래 총액을 플랫폼 수익으로 더하지 않는다. 매칭 상품 대금과 계약상 수수료를 구분하고 결제 비용·환불·할인 부담·사주 호출·운영 비용을 함께 본다. 무료 사주 이용자의 호출 비용도 비용 집계에 포함한다.

수수료 상태는 `pending → earned → settled`와 `reversed`를 구분한다. 업체의 이용 완료 확인, 취소·환불·정산 내역과 대사하고 중복 이벤트로 수수료가 두 번 쌓이지 않게 한다. 노쇼·부분환불의 정산 기준은 계약 확정 전 자동 추정하지 않는다.

## 6. 검증·운영 지표

정산 후 환불·부분환불은 기존 수수료 기록을 덮어쓰지 않고 원거래를 참조하는 조정 기록으로 남긴다.

필수 검증은 양쪽 조건 위반 계획 제외, 동의 후 가격 변경 감지, 중복 예약 방지, 외부 링크 클릭 시 미확정 유지, 업체 확인 없는 수동 확정 차단, 환불 이벤트 중복·역순 처리, 제3자 조회 차단이다. 공급자 장애 시 상태를 ‘확인 중’으로 유지하고 운영자가 대사할 수 있게 한다.

대시보드에는 활동 제안 수, 양쪽 동의 수, 예약 요청 수, 확정 수, 이용 완료 수, 취소·환불·노쇼 수, 대사 불일치, 수수료 발생·정산액을 구분한다. `양쪽 동의율=동의한 쌍/활동을 제안받은 쌍`, `예약 확정률=확정 예약/예약 요청`, `참석률=이용 확인 예약/확정 예약`처럼 분모와 관찰 기간을 고정한다. 동의·취소·만족도 개선과 비용을 함께 보고 수익성을 판단한다.

### 착수 전 미정 사항

업체 계약·500원 외 추가 과금 여부·수수료 부담 주체·가격 및 재고 제공 방식·확정 책임·개인정보 전달 범위·취소/환불/노쇼 정책·부분환불·영수증과 정산 절차는 아직 확정되지 않았다. Codex는 이 항목들을 설정·인터페이스로 분리하고, 실제 계약이 필요한 작업은 미연동 상태와 필요한 입력을 명확하게 남긴다.
