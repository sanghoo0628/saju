A 코드 리뷰 피드백 반영 (2026-11-23)

1. README
초기 README의 main 직접 push 금지, feature/fix 브랜치, PR→리뷰→merge,
커밋 접두사 규칙을 복원하고 기존 C 실행/상태 설명을 유지했다.
실제 학교 로그인/사주 저장/프로필/추천 확인 결과와 현재 검사 안내도 갱신했다.

2. 환불 후 재구매
실패하는 회귀 검사로 기존 pending 요청이 환불된 옛 주문에 묶이는 현상을 재현했다.
requestChat에서 같은 상대의 pending 요청만 새 fulfilled 주문으로 재연결한다.
SQL saveRequest도 order_id를 실제로 갱신하고 pending의 responded_at은 null로 유지한다.
기존 요청 ID와 시각은 유지하고, 주문 소유자·상대·결제 완료·차단·공개 조건은 그대로 확인한다.
거절된 요청은 다시 열지 않는다. 기존 수락/채팅방 및 환불 정책은 바꾸지 않는다.
DB 스키마 변경은 없다. 메모리·실제 SQL 매핑 및 native 동시 재시도 회귀 검사를 추가했다.

3. 진단 로그
createHttpApi의 onUnexpectedError를 Next 경계/런타임에 연결했다.
설정 오류도 기록하고 HTTP503은 유지한다. 바깥 catch에도 같은 안전한 기록을 적용했다.
이벤트·단계 및 허용 목록의 오류 이름/코드만 기록한다.
메시지, stack, URL, DB 쿼리/파라미터, 설정 키 목록, 임의 속성은 기록하지 않는다.
로깅 실패는 사용자 응답을 깨뜨리지 않는다. 유출 방지와 실제 경계 연결을 테스트했다.

4. CA
실제 dev pooler에 인증서 없이 엄격 TLS 연결 시 SELF_SIGNED_CERT_IN_CHAIN을 확인했다.
새 TLS 함수와 기존 로컬 CA를 쓰면 READ ONLY 트랜잭션과 SET LOCAL ROLE service_role 성공.
공유 DB 쓰기 없음. Supabase direct/pooler 주소는 DATABASE_SSL_CA_PATH를 필수로 확인한다.
다른 PostgreSQL 서버는 Node의 기존 신뢰 목록을 쓸 수 있고 인증서 검증은 항상 켜 둔다.
CA 파일 오류 시 검증을 끄거나 조용히 다른 설정으로 대체하지 않는다.

5. 거절 뒤 주문 응답
거절된 요청만 있고 채팅방이 없는 쌍에서는 createOrder가 chat_available이나 새 청구를
반환하지 않고 이전 거절 결과를 확인하라는 INVALID_REQUEST를 반환한다.
이는 기존 거절 후 재요청 금지 규칙의 표시/과금 방지 수정이며 새 환불 정책이 아니다.
기존 채팅방이 있으면 계속 무료로 이어간다.

6. CI
push: codex/c-payment-chat, feature/**, fix/**
pull_request 대상: main, codex/c-payment-chat
문서 제외, 읽기 전용 권한, 키 없는 격리 검사, 기존 동시 실행 취소 규칙은 유지한다.
