C 메시지·목록 시각 정밀도 보존
2026-11-23 / codex/c-payment-chat

문제
PostgreSQL created_at은 마이크로초 정밀도를 갖지만 pg 매퍼가 JS Date.toISOString으로 읽어 밀리초 아래 값을 잃었다.
화면도 Date.parse 결과만 비교해 같은 밀리초의 메시지를 UUID 순으로 재정렬할 수 있었다.
따라서 DB 페이지 조회 자체가 정확해도 화면에서 연속 메시지 순서가 뒤집힐 수 있었다.
같은 방식으로 정렬하던 대화 요청·방 목록에도 영향이 있었다.

변경
src/server/postgres-transaction.ts는 메시지/요청/방 조회에서 DB의 UTC 시각을 명시적 ISO 문자열로 읽는다.
고정 SQL to_char 표현을 사용하며 스키마·마이그레이션·DB 설정은 변경하지 않는다.
밀리초 아래 값이 실제로 있을 때는 6자리 소수를 보존한다.
밀리초 정밀도로 표현 가능한 시각은 기존 3자리 ISO 형식을 유지해 첫 전송/재전송 응답이 달라지지 않게 했다.
기존 ID 기반 커서 범위 검사와 DB 원본 timestamp 비교도 유지한다.

compare-timestamps.ts는 유효성이 확인된 시각을 밀리초와 그 아래 소수 부분으로 비교한다.
시간대가 다른 ISO 표현과 소수 자리의 trailing zero도 같은 시각으로 처리한다.
message-timeline은 오름차순, inbox-session은 내림차순에 이를 사용한다.
정확히 같은 시각일 때의 ID tie-break와 ID 기준 중복 제거는 그대로다.
API 필드·타입·가격·권한·결제 정책·브라우저 UI는 변경하지 않았다.

검증
회귀 테스트를 먼저 추가해 수정 전 [later, earlier]로 뒤집히는 실패를 확인했다.
수정 후 같은 테스트가 [earlier, later]로 통과했다.
추가 6개: 마이크로초 메시지 순서, 요청/방 목록 내림차순,
소수 정밀도·시간대/날짜 경계·동일 시각의 소수 표기·밀리초 우선 비교.
pg TCP + 실제 운영 SQL 매핑 + HTTP 어댑터 + 브라우저 클라이언트 + 화면 timeline을 이어 검증했다.
같은 밀리초 내 105개 메시지에 역순 ID를 지정하고 100+5 페이지를 읽었다.
실시간 decoder를 거친 중복 이벤트도 함께 반영했으며 결과는 105개, body 0~104 순서였다.
첫 두 시각 .000Z / .000001Z와 단건 조회의 정확한 timestamp 보존도 확인했다.
요청·방 목록의 .000002Z 보존과 다른 방 커서 거부를 함께 검증했다.
기존 메시지 재전송·중복 방지 검사도 통과했다.
