2 현재 서비스 기준
- 문과는 양수, 이과는 음수이며 생년월일에 대응하는 기본 숫자는 1~10,000이다.
- 같은 입력의 점수는 유지한다. 서버 비밀 키 기반 고정 생성 방식은 설계 제안이며 C가 점수 생성 기능을 구현한 것은 아니다.
- 매칭 거리는 abs(내 점수 + 상대 점수)이며 작은 순서로 3명을 추천한다.
- 사주 풀이와 매칭 숫자는 별개다. 매칭은 오락용이다.
- 추천 프로필 3명 및 상세 열람은 무료다.
- 선택한 한 상대에게 대화를 시작할 권한은 500원이다. 세 명 열람 상품이 아니다.
- 현재 구현 기준은 결제 확인 → 대화 요청 → 상대 수락 → 일대일 채팅이다.
- 같은 상대와 대화 재개, 받은 요청 수락 및 답장은 재결제를 요구하지 않는다.
- 결제는 상대의 수락/답장을 보장하지 않는다. 거절 이후 환불 정책 등은 팀 합의가 필요하다.
- 본인, 비공개, 탈퇴/비활성, 양방향 차단 대상은 추천에서 제외한다.

5 데모의 정확한 범위
화면 → 기존 C 브라우저 클라이언트 → 로컬 HTTP → 기존 C 서비스 → 데모 메모리 저장소로 동작한다.
인물은 모두 가상이며 실제 학생 데이터가 아니다.
데모 로그인은 demo-me로 고정되어 있다. 실제 인증 구현이 아니다.
결제 승인, 상대 수락과 상대 답장은 /api/demo/*의 명시적인 체험 버튼으로만 실행된다.
실제 결제/청구, Groble 연결, Supabase 저장/RLS/Realtime은 하지 않는다.
메시지 갱신은 2.5초 간격 조회이며 실제 Realtime 구독이 아니다.
데모 서버를 재시작하면 메모리 데이터는 초기화된다.
demo/와 demo-client.ts, 가상 catalog는 운영 코드에 포함하지 않는다.

8 B에게 받은 자료와 수정 요청
마지막 확인한 main 커밋: 31d1941.
자료: docs/CONTRACT_profile_matching.md, supabase/migrations/0002_profiles_matching.sql.
B는 PostgreSQL 16의 Supabase Auth 유사 환경에서 테스트했다고 설명했으며 실제 Supabase에는 미적용이라고 했다.
해당 자료는 기존 유료 추천 방식 및 사주 0~100 궁합 계산을 사용하고 있어 현재 C와 바로 연결할 수 없다.
사용자는 다음 수정 요구를 B에게 전달했다고 확인했다:
- 프로필 3명 무료 공개, 선택한 상대별 500원
- 문과 양수/이과 음수 및 점수 합 절댓값 오름차순 유지
- 추천 결과를 주문과 분리하고 고유 ID, 추천받은 사용자 ID, 상대 ID 제공
- 결제 시작 시 전체 후보 3명 조건 대신 선택한 상대의 유효성 검증
- 결제 확정에서 create_match_for_order를 호출하지 않음
- C 상태 pending/fulfilled/cancelled/refund_pending/refunded로 계약 조정
- 채팅 RLS에서 참여자와 양방향 차단을 함께 확인
수정된 계약/SQL 답변은 아직 받지 않았다.
공개 profiles와 비공개 profile_saju 분리 및 auth.users.id 통일은 활용할 수 있다.
B가 제안한 chat_rooms/chat_participants/chat_messages 이름은 실제 DB 어댑터에서 맞출 수 있다.
기존 B SQL은 C 브랜치에 임의로 수정하거나 병합하지 않았다. 아직 C의 실제 0001/0003 SQL을 작성/적용하지 않았다.

9 남은 구현
- A 공통 앱과 검증된 로그인 세션 연결
- B 수정 스키마를 기준으로 C 주문/결제/채팅 SQL, 실제 트랜잭션과 RLS 통합
- Groble 상품 ID, 500원 지원, 협찬 수수료, 테스트 결제, 서명 검증과 이벤트 명세 확인
- 실제 Groble 결제창 이동과 결제 복귀 주문 식별 방법 연결
- 실제 웹훅/환불 이벤트, 환불 실행·재시도·운영 처리
- Supabase Realtime 구독 및 snake_case → ChatMessage 변환
- 차단/신고 생성 API, 요청/메시지 속도 제한
- 메시지 POST 재시도용 서버 멱등 키는 아직 없다. 현재는 자동 재전송하지 않으며 전송 중 버튼을 비활성화한다.
- 환불 후 기존 채팅 존속, 거절 시 환불, 성별/희망 조건, 점수 입력 수정 정책 등 팀 합의
- 실제 사용자 두 계정과 제3자 계정으로 결제·RLS·채팅 통합 검증
비밀 키는 채팅/Git에 넣지 않고 서버 환경 변수로 관리한다.
