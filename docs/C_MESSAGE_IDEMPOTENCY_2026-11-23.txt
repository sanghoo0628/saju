C 채팅 응답 유실·중복 전송 방지
2026-11-23 / codex/c-payment-chat

문제와 변경
메시지가 DB에 저장된 뒤 POST 응답만 유실되면 재전송 시 같은 내용이 두 번 저장될 수 있었다.
브라우저에서 한 번의 전송에 UUIDv4 clientMessageId를 만들고, 명시적 재전송에는 같은 ID와 본문을 사용한다.
서버는 이 값을 기존 messages.id로 저장한다. 같은 사용자·방·정규화한 본문의 재전송은 최초 메시지와 시각을 반환한다.
다른 사용자·방·본문으로 이미 쓰인 ID를 재사용하면 INVALID_REQUEST로 거절한다.
매 요청에서 현재 참여자·양방향 차단부터 검사하므로 과거 성공한 전송도 현재 권한을 우회하지 않는다.

API 및 DB 계약
POST /api/conversations/:id/messages의 기존 body 필드는 유지한다.
선택 필드 clientMessageId를 추가했다. 소문자 표준 UUIDv4 형식만 허용한다.
기존 body-only 호출도 동작하지만 해당 호출은 전송마다 새로운 ID가 생성된다.
client.sendMessage(room, body, signal?, clientMessageId?)의 기존 인자 순서는 유지한다.
Transaction.message(id) 조회와 messages_pkey 충돌 재시도를 추가했다.
SERIALIZABLE 트랜잭션에서 경쟁 insert 실패를 롤백한 후 기존 메시지를 다시 확인한다.
마이그레이션·공유 DB 설정·금액·주문/수락 정책은 변경하지 않았다.
B의 기존 messages PK를 그대로 사용하므로 새 컬럼이나 SQL 배포가 필요 없다.

화면 처리
응답 실패 시 전송 시도를 메모리에 보관한다. 자동 POST 재시도는 하지 않는다.
대화 기록 확인 또는 이전 메시지 다시 보내기를 제공한다.
재전송 버튼은 최초 본문과 ID를 사용한다. 실패 후 수정한 다음 초안은 그대로 둔다.
처리 여부가 미확정인 동안 바뀐 본문을 새 메시지로 보내려 하면 먼저 이전 상태를 확인하도록 안내한다.
POST 응답뿐 아니라 일치하는 Realtime/기록 조회 결과로도 전송 완료를 확인한다.
사용자·방마다 추적하며 화면을 벗어나면 제거한다. 새로고침 후 복구 기능은 포함하지 않는다.
localStorage/sessionStorage에 메시지 본문을 새로 저장하지 않는다.

로컬 검증
기본 회귀 376개: B/SQL 114 + C 147 + A 97 + UI 18, 모두 통과.
ESLint, 타입 검사, Next.js build, 독립 Vite build, 로컬 HTTP 20개 통과.
추가 단위 검사는 응답 유실 후 재전송, 본문/작성자/방 충돌, 차단 후 재시도,
구형 요청 호환, 확인 추적·초안 유지 관련 상태를 검증한다.
격리된 SQL 검사에서는 최초 결과 반환·본문/작성자 충돌 및 차단 재검사를 확인했다.

브라우저 장애 재현
공유 Supabase 대신 별도 메모리 데모 및 임시 로컬 장애 프록시를 사용했다.
첫 POST는 실제 데모 저장 후 503으로 응답하고, 재전송 전까지 기록 조회에서 숨겼다.
이후 초안을 수정하고 기존 메시지 재전송 버튼을 눌렀다.
관측 결과: POST 2회, 고유 전송 ID 1개, 저장된 메시지 1개.
화면에도 원래 메시지 한 개가 표시됐으며 수정한 다음 초안은 유지됐다.

네이티브 PostgreSQL 검사
기존 10개에 12개 동시 재전송이 한 행으로 수렴하는 검사와,
같은 ID/다른 본문 경쟁에서 하나만 성공하는 검사를 추가했다(합계 12개).
기본 운영 재시도 한도 5를 사용한다.
로컬 환경의 System V IPC 제한으로 native 검사는 GitHub Linux CI에서 확인한다.
CI 결과는 확인 후 이 문서에 기록한다.

이번 작업에서는 공유 Supabase 데이터나 스키마에 쓰지 않았고 실제 결제도 실행하지 않았다.
A/B 사주 결과 저장 연결, 실제 학교 메일 수신, Groble 공식 연동은 기존 대기 항목이다.
main과 A/B 브랜치는 수정하지 않는다.
