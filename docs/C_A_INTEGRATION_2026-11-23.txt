실제 코드 연결
- /matches: B 무료 추천 API 결과를 카드로 표시하고 results[].id를 C matchResultId로 전달한다.
  1~3명만 있으면 실제 인원만 표시한다. 후보를 가짜로 채우지 않는다.
  생년월일·점수·이메일·사주 원문을 프로필 카드에 전달하지 않는다.
- /requests, /chat: C ChatPanel + inbox-session + 인증된 Supabase message source 연결.
  요청 목록 자동 조회, 수신자 무료 수락/거절, 본인 대화 선택, 메시지 전송·복구를 재사용한다.
  공개 닉네임/학과 조회는 브라우저 RLS를 적용한다. 긴 ID 목록은 50개씩 조회한다.
- /orders/return: 사용자별 sessionStorage에 남은 기존 주문만 서버에 재조회한다.
  URL의 성공 표시로 권한을 만들지 않는다. 주문이 없으면 추천 화면으로 안내한다.
- /api/orders, /api/chat-requests, /api/conversations 및 각 하위 경로를 C createHttpApi에 탑재했다.
  원래 C의 {code,message} 응답, Origin 검사, raw webhook 본문, 소유권·참여자·차단 검사를 유지한다.
- /api/match-results, GET/PUT /api/profile을 B MatchingService에 연결했다.
  프로필 화면 자체는 아직 B 연결 대기 안내다. 새 UI를 임의로 완성했다고 보고하지 않는다.
- A requireVerifiedSchoolUser로 요청마다 Auth user.id와 학교 도메인/확인 상태를 검사한다.
  인증 정보를 전역에 캐시하지 않는다. 구성/인증 오류는 C 응답 형식으로 변환한다.
- payment-chat-runtime은 server-only, Node.js 런타임이며 첫 요청에서 인프라만 생성·재사용한다.
  DB 풀과 서비스만 캐시하고 사용자 신원은 캐시하지 않는다. 빌드 중 DB 접속·마이그레이션 없음.
- pg에는 DATABASE_SSL_CA_PATH의 CA와 rejectUnauthorized=true를 전달한다.
- 로그아웃·계정 변경 시 C 화면/구독/상태 작업을 정리한다.
- C CSS를 .payment-chat-experience 범위에 적용해 A 헤더·사주 화면과 충돌하지 않게 했다.
  독립 Vite 데모도 같은 범위에서 표시한다. 데모 App/catalog/server는 Next에 가져오지 않는다.

Groble 상태 — 실제 결제는 아직 미연결
- 공식 서명/상품/웹훅 규격이 없어 런타임에 성공 mock을 넣지 않았다.
- 새 주문의 checkout URL 생성과 웹훅 확정은 PROVIDER_UNAVAILABLE(503)로 거부한다.
- 주문 생성 실패 시 저장되는 신규 주문이 없음을 격리 SQL에서 확인했다.
- 기존 fulfilled 주문·기존 대화방·받은 요청·무료 수락·채팅은 gateway와 독립적으로 동작한다.
- PAYMENTS_ENABLED=true 또는 MOCK_PAYMENTS_ENABLED=true는 여전히 거부한다.
  flag나 URL/키만 넣는 것으로 실제 결제가 활성화되지 않는다.
- 새 결제창 이동/allowlist/출발 주문 저장은 공식 gateway를 붙일 때 기존 checkout-return 모듈로 연결한다.
  이번에는 복귀 화면의 기존 주문 조회까지 연결했다. 실제 결제 이동을 검증한 것은 아니다.

실제 계정으로 남은 확인
1. 같은 프로젝트의 publishable/secret API 키를 대시보드에서 확인해 로컬 env에만 설정한다.
   DB 접속 정보와 SCORE_HMAC_SECRET은 이미 저장되어 있으니 다시 덮어쓰거나 바꾸지 않는다.
2. A/B가 사주 결과 저장을 연결해야 신규 사용자가 프로필/추천을 만들 수 있다.
   현재 A HRUM 응답은 persistence=not_persisted이며 B의 base_number/score 등 필수 값이 자동 생성되지 않는다.
   기존 HMAC 점수와 HRUM 강약 분석을 임의로 같은 값으로 취급하지 않았다.
   원래 계열 입력·달력 일자·동의/저장 계약을 A/B가 맞춰야 한다.
3. 실제 학교 이메일 계정 2개와 제3자 계정으로 로그인, 요청·수락, 송수신,
   차단, 로그아웃/계정 전환, 재연결 및 RLS/Realtime 실제 전달을 검증한다.
4. Groble 공식 답변 후 검증된 gateway, 상품, 원문 서명, 복귀 URL, 환불 규격을 연결한다.
   거절 후 환불 같은 미정 상품 정책을 임의로 정하지 않는다.
