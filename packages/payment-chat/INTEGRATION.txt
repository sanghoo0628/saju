현재 과금 기준
- 추천 프로필 3명은 무료로 공개한다. 무료 추천 API와 프로필 화면은 B 담당이다.

- 결제만으로 상대의 수락을 보장하지 않는다. 거절 이후 자동 환불 여부 등 상품 정책은 팀 합의가 필요하다.

HTTP 계약
POST /api/orders                          { matchResultId } → 결제 링크 또는 기존 대화 권한
GET  /api/orders/:id                      → 주문 상태와 선택한 상대 ID
POST /api/webhooks/groble                 → 제공자 서명을 검증할 원문 body
POST /api/chat-requests                   { orderId } → 대화 요청
GET  /api/chat-requests?afterId=...        → 본인이 주고받은 요청
POST /api/chat-requests/:id/accept         빈 body 또는 {} → 채팅방 ID
POST /api/chat-requests/:id/reject         빈 body 또는 {} → 거절된 요청
GET  /api/conversations?afterId=...        → 본인이 참여한 채팅방
GET  /api/conversations/:id/messages?afterId=... → 기록 조회
POST /api/conversations/:id/messages       { body } → 저장된 메시지
목록은 최대 100개다. 요청/대화 목록은 생성 시각과 ID 최신순, 메시지는 오래된 순이다.
다음 조회에는 직전 페이지 마지막 항목의 id를 afterId로 전달한다.
요청 응답 식별자는 requestId가 아니라 id로 통일했으며 createdAt도 포함한다.
공개 프로필 3명 조회 API는 B 담당이므로 이 유료 대화 어댑터에서 처리하지 않는다.

Next.js 연결 예시
  // A의 공통 서버 모듈에서 실제 repository/gateway/getCurrentUserId를 준비한 뒤:
  const service = createService({ repository, gateway });
  const handlePaymentChat = createHttpApi({
    service,
    getCurrentUserId: () => getCurrentUserId(),
    appOrigin: process.env.NEXT_PUBLIC_APP_URL,
  });
  // 각 app/api/.../route.ts에서 해당 메서드만 내보낸다:
  export const POST = handlePaymentChat;
  // 조회 경로에서는 export const GET = handlePaymentChat;
  // Node 서버용 모듈이므로 export const runtime = 'nodejs'; 사용.
실제 모듈 import 경로와 환경 변수 존재 여부 검사는 A 앱 구조에 맞춘다.
getCurrentUserId는 요청마다 실행되어야 하며 사용자 ID를 모듈 전역에서 캐시하면 안 된다.
브라우저 POST는 appOrigin과 정확히 일치하는 Origin을 요구한다.
로컬 개발과 배포에서 각각 올바른 앱 주소를 지정한다. 웹훅은 이 Origin 검사에서 제외된다.
주문/채팅 응답은 Cache-Control: no-store다. 브라우저에 서버 오류 원문을 반환하지 않는다.
브라우저 createOrder() 결과가 chat_available이면 재결제하지 않고 기존 요청/대화로 연결한다.
payment_required일 때만 checkoutUrl로 이동한다. 복귀 후 order() 상태가 fulfilled일 때 요청 가능하다.
pending이면 결제 확인 중을 표시하고, refund_pending이면 환불 안내로 전환한다.

  const unsubscribe = flow.subscribe(state => updateUI(state));
  // 프로필의 명시적인 대화 시작 버튼에서만 호출한다.

  // Groble 복귀 화면에서 알고 있는 주문 ID로 조회한다. URL의 성공 표시는 신뢰하지 않는다.

기본값은 2초 간격, 최대 15회 및 30초 제한이다. 응답이 없으면 confirmation_pending으로
주문 ID를 유지한다. 이 상태의 다시 확인 버튼은 resume(orderId)이며 새 주문을 만들지 않는다.
재시도는 주문 상태 GET에만 적용한다. 권한/로그인 오류는 중단하며 5xx/네트워크 오류는 제한 안에서 재시도한다.
refund_pending/refunded/cancelled는 결제 성공으로 취급하지 않는다.
flow.reset()은 화면 작업만 멈춘다. 결제/주문 취소 기능이 아니다.
화면 해제 또는 로그아웃/사용자 변경 때 unsubscribe() 및 flow.dispose()를 호출한다.
상태 모듈은 주문 ID를 브라우저 저장소에 저장하지 않는다. 복귀 시 주문 식별자 전달 방법은
A의 화면 흐름 및 Groble 실제 복귀 설정에 맞춘다. 주문 접근 권한은 항상 서버에서 재검증한다.

채팅 화면 상태 연결

  // Supabase 어댑터에서 변환한 Realtime 이벤트와 전송 성공 응답을 모두 receive로 전달한다.
  timeline.receive(message);
  // 기록 조회 전 요청 토큰을 보관한다.
  const token = timeline.nextHistoryPage();
  const page = await client.messages(conversationId, token.afterId);
  timeline.appendHistory(page, token);
  // snapshot().messages를 렌더링하고 historyComplete=false이면 다음 페이지를 이어서 조회한다.
실시간 최신 메시지를 받아도 historyCursor는 바뀌지 않는다. 그래야 아직 읽지 않은 DB 기록을 건너뛰지 않는다.
Realtime을 먼저 구독하고 기록을 조회한다. 같은 ID는 합쳐 한 번만 표시한다.
연결 복구 시 timeline.restartHistory() 후 첫 페이지부터 historyComplete가 될 때까지 조회한다.
restartHistory 이전의 늦은 응답은 토큰 버전으로 거부한다. 마지막 실시간 ID를 기록 커서로 사용하지 않는다.
로그아웃, 권한 상실, 차단 오류 시 timeline.clear()로 화면의 기존 기록도 제거한다.
다른 방의 이벤트와 잘못된 이벤트는 무시한다. snake_case DB 행은 Realtime 어댑터가
ChatMessage(id, conversationId, senderId, body, createdAt)로 변환해야 한다.
이 모듈은 동일 ID의 중복 표시를 막는다. 메시지 POST 재시도에 대한 서버 멱등 키는 아직 없으므로
전송 실패를 자동 재시도하지 않는다. 전송 중 중복 클릭은 화면에서 비활성화해야 한다.

A에게 필요한 연결
- 공통 앱/패키지 매니저, 서버 로그인 세션, API 오류 변환 및 입력 검증.
- 이 패키지는 서버에서만 불러온다. 프론트에는 서비스 구현이나 비밀 키를 전달하지 않는다.

A의 연동 규약 제안 반영
- Next.js App Router, TypeScript, pnpm을 사용하자는 제안이다. 공통 앱 생성이나 main 업로드 완료 통보는 아니다.
- C는 user.id 문자열을 Actor.userId로 사용한다. DB는 Supabase Auth UUID를 참조한다.
- 서버 연결 지점은 src/lib/auth/get-current-user-id.ts의 getCurrentUserId(): Promise<string | null>이다.
  함수의 실제 생성 경로와 쿠키 갱신 처리는 A 코드 수령 후 확인한다.
- 실제 DB 컬럼은 orders.buyer_id, chat_requests.requester_id/recipient_id,
  messages.sender_id로 제안되어 있다. B와 합의한 뒤 어댑터에서 C의 userId/from/to/senderId에 매핑한다.
- 웹훅에는 로그인 세션을 요구하지 않는다. 서명 검증 후 저장된 주문 참조값으로 구매자를 찾는다.
- A에게 공통 Node/pnpm 버전과 pnpm-lock.yaml 및 실행 README 공유를 요청한다.
  C의 독립 테스트는 Node 24 이상을 요구하므로 공통 Node 버전과 호환성을 맞춰야 한다.
- pnpm 기반 실행은 저장소 루트에서 pnpm --dir packages/payment-chat test로 가능하다.
- 기존 PDF 및 A의 답변에 남은 '500원 결제 후 프로필 3명 공개'는 폐기된 흐름이다.
  올바른 흐름은 무료 추천 3명 공개 → 상대 선택 → 상대당 500원 결제 → 대화 요청 → 수락 → 채팅이다.
  결제 전에 후보 3명 이상인지 검사하거나 결제 후 3명을 새로 선정하지 않는다.
- 환경 변수 예시는 A의 공통 .env.example에 모은다. 실제 키는 Git과 채팅에 기록하지 않는다.
  GROBLE_PAYMENT_URL/GROBLE_WEBHOOK_SECRET은 프로젝트 변수명 제안이며 실제 제공자 검증 명세는 별도 확인한다.

B에게 필요한 연결
- 무료 추천 결과는 id, userId, targetId를 가진다. userId는 추천받은 사용자다.
- 프로필 공개 동의/활성 상태와 양방향 차단 상태 확인 기능.
- 결제와 채팅 저장용 DB 트랜잭션 및 RLS. transaction 콜백을 각각의 Supabase REST
  호출로 구현하면 원자성이 보장되지 않는다. DB 함수/RPC 등 하나의 실제 트랜잭션으로 구성한다.
- 주문 참조값과 결제 거래 ID의 고유 제약, 사용자-상대별 활성 주문 및 요청 고유 제약,
  두 참여자의 순서와 무관한 채팅방 고유 제약과 동시 요청 직렬화가 필요하다.
- messages 조회/전송 및 Realtime 구독은 참여자만 허용한다. 이 패키지의 서버 검사는 RLS를 대체하지 않는다.
- 메시지는 DB 저장 후 Realtime으로 전달한다. 조회는 최대 100개, 시각과 ID 정렬 및 커서 검증이 필요하다.
- requestsForUser/conversationsForUser는 본인 관계만 조회하고 차단을 제외한 뒤 페이지를 구성한다.
  다른 사용자의 항목을 afterId로 전달하면 거부한다. 요청과 채팅방에는 createdAt을 저장한다.

Groble 연결 전 필요한 사항
- 상품 ID, 500원 지원, 테스트 결제, 서명 헤더와 원문 검증 규격, 이벤트/환불 명세.
- PaymentGateway.verifyCompleted는 실제 완료 이벤트만 검증 후 내부 형식으로 변환한다.
- 웹훅은 raw body를 사용한다. JSON을 파싱 후 재직렬화한 내용을 서명 검증에 사용하지 않는다.
- 잘못된 서명은 ServiceError('INVALID_WEBHOOK', ...)로, 일시적 제공자 장애는
  ServiceError('PROVIDER_UNAVAILABLE', ...)로 구분한다. HTTP 어댑터는 각각 400/503을 반환한다.
- 결제 이후 상대 비공개/차단은 refund_pending으로 기록한다. 실제 환불 실행과 재시도 작업은 아직 미구현이다.
- 비완료 이벤트, 취소/환불 웹훅, 운영 오류 재시도 및 관리자 처리는 실제 명세에 맞춰 추가해야 한다.

아직 제공하지 않는 것
- 공통 Next.js 앱에 탑재한 라우트와 화면, 실제 Groble 검증/결제 연결, Supabase DB/RLS/Realtime 어댑터.
- 차단·신고 생성 API, 요청/메시지 속도 제한, 운영 환불 처리.
- packages/payment-chat-ui에 독립 React 화면 데모를 추가했다. 실행과 통합 방법은 해당 폴더의 INTEGRATION_UI.txt 참고.
- 화면 데모는 기존 C HTTP/서비스 로직과 로컬 메모리 저장소로 동작하며, 실제 Realtime 구독은 아직 연결하지 않았다.
- 현재 차단은 요청/수락/메시지/기록 조회를 거부한다. 기존 채팅방의 환불 후 존속 정책은 팀 합의 후 반영한다.
- 프로필 무료 공개도 생년월일·학교 이메일·전체 사주 원문 공개를 뜻하지 않는다.

저장소 구성
- 공통 프로젝트와 충돌하지 않도록 독립 패키지로 작성했다. 루트 앱 초기 설정은 변경하지 않았다.
- C 모듈은 루트 contracts/ 및 packages/payment-chat/에 있다. 공통 앱 경로는 A 통합 시 확인한다.
- A의 실제 앱 생성 이후 import와 실행 설정을 연결한다.

검증 범위
- 동작 테스트 61개 및 개발 중 TypeScript strict 정적 검사를 통과했다.
- 가짜 세션/결제/DB로 브라우저 호출 함수 → HTTP 어댑터 → 핵심 로직까지 검증했다.
- 실제 브라우저 UI, Supabase 인증/RLS, Groble 결제, 네트워크 Realtime 검증은 아직 하지 않았다.
- 정적 검사 도구는 공통 프로젝트 의존성을 임의로 바꾸지 않도록 별도 작업 캐시에서 실행했다.
  A의 TypeScript/Node 설정 수령 후 공통 typecheck 스크립트에 통합한다.
